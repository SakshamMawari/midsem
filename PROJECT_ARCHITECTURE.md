# Study Library: Plan and Architecture

## Project goal

Study Library is a static-first website for browsing study material using the hierarchy:

```text
Subject → Unit → PDF
```

The repository folder structure is the content source of truth. Adding a PDF should only require placing it in the correct folder and pushing the change.

## Implementation plan

The project was implemented in this order:

1. **Scaffold**
   - Next.js App Router
   - TypeScript with strict checking
   - Tailwind CSS
   - npm package management

2. **Manifest generation**
   - Scan `public/library`
   - Read optional subject and unit metadata
   - Derive names when metadata is absent
   - Collect PDF paths, file sizes and page counts
   - Detect duplicate file slugs

3. **Static routes**
   - Home subject listing
   - Subject unit listing
   - Unit PDF listing
   - Individual PDF reader page
   - `generateStaticParams` for all content routes

4. **PDF viewer**
   - PDF.js client component
   - URL-based PDF loading
   - Lazy rendering for pages near the viewport
   - Zoom and fit-to-width controls
   - Page indicator and keyboard navigation
   - New-tab fallback when rendering fails

5. **Design and accessibility**
   - Dark-only interface
   - Responsive layouts
   - Search box
   - Breadcrumbs
   - Empty states
   - Semantic HTML
   - Visible focus states
   - Reduced-motion support

6. **Deployment**
   - Vercel-compatible configuration
   - Long-lived cache headers for PDFs
   - Revalidating cache headers for HTML
   - Optional HTTP Basic Auth
   - Environment-controlled indexing

7. **Documentation**
   - Setup and content instructions in `README.md`
   - This architecture and implementation record

## Content architecture

### Folder source of truth

PDFs are stored at:

```text
public/library/<subject-slug>/<unit-slug>/<file>.pdf
```

The manifest script ignores non-PDF files except for optional metadata:

- `subject.json`
- `unit.json`

Placeholder `README.txt` files are used to keep empty seeded units visible in Git.

### Subject metadata

Example:

```json
{
  "name": "Mathematics for Data Science",
  "icon": "∑",
  "order": 1
}
```

### Unit metadata

Example:

```json
{
  "name": "Vector Spaces",
  "description": "Fields, vectors and core definitions.",
  "order": 1
}
```

### Name fallback

When metadata is missing, names are generated by replacing hyphens and underscores with spaces and applying title case.

## Manifest pipeline

The manifest is generated by [`scripts/build-manifest.ts`](./scripts/build-manifest.ts).

It:

1. Creates `public/library` if needed.
2. Scans subject directories.
3. Reads `subject.json` when present.
4. Scans unit directories.
5. Reads `unit.json` when present.
6. Finds `.pdf` files.
7. Generates URL-safe file slugs.
8. Records:
   - Display name
   - Public URL path
   - File size in MB
   - Approximate page count when detectable
9. Fails if two files in one unit generate the same slug.
10. Writes `src/data/manifest.json`.

The script runs automatically through:

```json
{
  "predev": "npm run manifest",
  "prebuild": "npm run manifest"
}
```

The manifest freshness and duplicate-slug check can also be run directly:

```bash
npm run test:manifest
```

## Application architecture

### Server-rendered pages

The route pages are server components and read from the generated manifest:

- `app/page.tsx`
  - Renders all subjects.
- `app/[subject]/page.tsx`
  - Renders units for one subject.
- `app/[subject]/[unit]/page.tsx`
  - Renders PDFs for one unit.
- `app/[subject]/[unit]/[file]/page.tsx`
  - Renders metadata and the client PDF reader.

Each dynamic route provides `generateStaticParams`, so content known at build time is pre-rendered.

### Shared library helpers

[`src/lib/library.ts`](./src/lib/library.ts) provides:

- Subject lookup
- Unit lookup
- File lookup
- File size formatting
- PDF URL generation

The `getPdfUrl()` helper centralizes PDF storage. It uses:

```text
NEXT_PUBLIC_PDF_BASE_URL
```

and defaults to:

```text
/library
```

This allows PDFs to move to Vercel Blob, Cloudflare R2 or another CDN without changing route components.

### Client components

- `Header.tsx`
  - Global branding and search.
- `SearchBox.tsx`
  - Client-side filtering across subject, unit and PDF names.
- `PdfReader.tsx`
  - PDF.js loading and page rendering.

## PDF reader design

The PDF reader uses `pdfjs-dist` in a client component.

### Loading

PDF.js receives the public PDF URL directly rather than a preloaded `ArrayBuffer`. This lets the browser and hosting layer use HTTP range requests for large files.

### Lazy rendering

The reader creates lightweight page containers for all pages. An `IntersectionObserver` renders a page only when it enters or approaches the viewport.

### Controls

- Zoom out
- Zoom in
- Fit to width
- Current page indicator
- Arrow Up / Page Up navigation
- Arrow Down / Page Down navigation

If PDF.js fails, the interface presents a normal link to open the file in a new browser tab.

## Routing and URL model

```text
/                                      Subject index
/<subject>                             Unit index
/<subject>/<unit>                      PDF list
/<subject>/<unit>/<file>               PDF reader
```

File links use generated slugs in application routes while the actual PDF URL preserves the original filename through `getPdfUrl()`.

## Search architecture

Search is intentionally client-side because all content metadata is available in the generated manifest.

The search query is matched against:

```text
subject name + unit name + file name
```

The search result list links directly to the PDF reader route.

## SEO and indexing

The root layout provides:

- Default title
- Per-page title template
- Description
- Open Graph metadata
- Favicon
- Robots configuration

Indexing is disabled by default. It is enabled only when:

```text
SITE_INDEXABLE=true
```

The `/robots.txt` route uses the same environment variable.

## Optional password protection

[`proxy.ts`](./proxy.ts) implements an optional HTTP Basic Auth gate.

Behavior:

- `SITE_PASSWORD` unset: requests pass through.
- `SITE_PASSWORD` set: requests require Basic Auth.
- The password is compared server-side in the proxy.

The gate is optional and does not require a database or user system.

## Deployment architecture

The site is designed for Vercel with no custom server:

```text
Git repository
    ↓
Vercel build
    ↓
Manifest generation
    ↓
Next.js static generation
    ↓
Static HTML, JavaScript, CSS and PDF assets
```

`vercel.json` sets:

- One-year immutable caching for `/library/*`
- Revalidating caching for application HTML

PDF files are marked as binary in `.gitattributes`.

## Environment variables

| Variable | Default | Purpose |
| --- | --- | --- |
| `SITE_INDEXABLE` | `false` | Enable search-engine indexing when set to `true`. |
| `SITE_PASSWORD` | unset | Enable optional HTTP Basic Auth. |
| `NEXT_PUBLIC_SITE_URL` | `http://localhost:3000` | Base URL for metadata. |
| `NEXT_PUBLIC_PDF_BASE_URL` | `/library` | Base URL for PDF files. |

## Current assumptions and limitations

- The seeded repository initially contains no real PDFs, so empty-unit states are expected until PDFs are added.
- Page counts use a lightweight byte scan and may be unavailable for some PDFs.
- The static manifest must be regenerated whenever content changes; `predev` and `prebuild` do this automatically.
- PDFs committed to Git are suitable for smaller collections. Larger collections should use object storage and `NEXT_PUBLIC_PDF_BASE_URL`.
- The local runtime smoke test may be restricted in environments that disallow binding to localhost ports, but the production build is the primary deployment validation.
